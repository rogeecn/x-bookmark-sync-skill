# 排版规范：一条书签 = 一张卡片

这份规范是本 skill 的主体。`scripts/render.py` 是它的实现，改排版请两边一起改。

## 为什么是「卡片」而不是「一段文字」

memos 是瀑布流列表，用户扫读，不是阅读。历史同步（771 条）的形态是「作者链接 + 原文」平铺，最长的 3222 字符一坨，扫读时无法判断「这条值不值得点开」。

卡片的三个职责：

1. **3 秒内回答「这是什么、谁说的、值不值得看」** —— 靠标题行 + byline 完成。
2. **不点开也是完整信息** —— 正文/引用/媒体全部内联，不依赖外链。
3. **想深挖时有路径** —— 原推、完整文章、原始链接都在，但排在后面，不干扰扫读。

## 官方数据里被历史同步丢掉的字段

twitter-cli 的 bookmarks JSON 每个对象都带这些，历史 memo 一个都没用：

| 字段 | 用在哪 | 为什么值得用 |
| --- | --- | --- |
| `metrics.*` | 默认不显示，`--metrics` 才出 | 扫读列表时热度是干扰项：容易被「3.8k 赞」牵着走而不是看内容。需要筛选时再开 |
| `createdAtISO` | byline | 存档要能追时间线；同年只显示 `MM-DD`，省 4 个字符 |
| `author.name` | byline 链接文字 | 人认得的是名字，不是 handle；handle 只留作 href，点得到就够了。`✓` 认证标记也不显示：它不改变内容价值 |
| `quotedTweet`（完整对象，非仅链接） | 引用块 | 转推的评论往往只有一句，**实体在引用推里**；历史只贴了链接，价值损失最大 |
| `media[].type/width/height` | 媒体区 | 视频在历史里直接丢失；照片可用高分辨率 rendition |
| `articleTitle` | 标题 | X 长文有真标题，比截断首行好 |
| `urls[]` | 链接区 | 推文里的资源链接，值得单独列成预览卡（但数量常对不上，见正文第 3 条） |
| t.co 的 301 目标 | 正文内联 | 唯一可信的展开来源：`urls[]` 缺、多、错位都能在这里补回来 |
| `isRetweet` / `retweetedBy` | byline | 说明「这不是他原创」，影响可信度判断 |
| `lang` | —（暂不用） | 预留：可给非中文内容加语言标记 |
| `score` | —（不用） | twitter-cli 内部排序分，对读者无意义 |

另外 `twitter article <id> -m` 能拿到长文全文（推文里只有摘要 + 链接），历史同步从未取过。

## 结构（自上而下，顺序即优先级）

```
### 标题
[@名字](https://x.com/handle) · 11-16 19:36

正文（t.co 已展开）

> **@引用作者** 名字 · [引用](https://x.com/…/status/…)
>
> 引用正文

![](照片?name=large)
🎬 [视频 · 1920×1080](https://video.twimg.com/…)

**🔗 链接**
https://github.com/…

<details><summary>📄 全文 · 4820 字</summary>

文章全文

</details>

[原推](https://x.com/…/status/…) · 存档 2026-11-17
#Twitter #Bookmark #github
```

### 1. 标题：`###`，不是 `#`

- memos v0.30 的字号阶梯：h1=1.5×、h2=1.25×、h3=1.125×、h4–h6=正文字号。
  瀑布流里 h1/h2 会像页面标题一样压过相邻卡片，**h3 是「卡片标题」那一档**。
- 标题来源优先级：用户改写 > `articleTitle` > 推文首行（≤70 字且剩余 ≥30 字时抽出，正文中去掉避免重复）> 首行截断到 60 字（在标点处断，加 `…`）。
- 首行被抽走后一定要从正文删掉，否则同一句话出现两次，这是最常见的观感 bug。
- 不要用代码块/引用块当标题：memos 列表里预览卡会变形。

### 2. byline：名字 + 时间，两段就够

`[@名字](https://x.com/handle) · 11-16 19:36`

- **名字当链接文字**，handle 只作 href。读者在时间线里扫的是「谁说的」，`[@Khazix0918]` 不如 `[@数字生命卡兹克]`；点进去照样到他主页。
- **不显示热度**（浏览/收藏/赞/回复/转推/引用）。它们原本在 byline 尾部，看起来像筛选器，实际是干扰：3.8k 赞的判断会盖过读者的判断。真要看，`--metrics` 打开，或者去原推看。
- **不显示 `✓` 认证标记**：它不改变内容本身的价值，只是平台状态。
- 只保留**转发标记** `🔁 @谁`：这条不是他原创，这个信息影响可信度。
- 时间只显示 `MM-DD HH:MM`（跨年才带年份），顺手就是时间线锚点。
- 缺字段就不出现那一段，不要留空的 `·`。
- 已被旧版渲染过的 memo 不用重发：`repair --in-place` 会在原 memo 上把这一行改写成上面的形态。

### 3. 正文

- 保留原文换行。memos 用 `breaks:true`（单换行即换行），所以照抄推文换行是对的。
- **t.co 必须换成真实地址**，否则读者看不出这条链接去哪，memos 也只能给 t.co 生成一张没信息的预览卡。
  twitter-cli 的 `urls[]` 靠不住：200 条书签里 100 条的短链数 ≠ `urls` 数（多则 10 vs 5，少则 1 vs 0），按序替换会把句子指向错误站点。所以换成**跟着 301 走**：`plan` 用 curl 逐条请求 t.co（走 `$TWITTER_PROXY`，`socks5h` 让 DNS 在代理侧解析），拿到 `url_effective` 写进 `plan.json` 的 `links` 再渲染。实测 280 条唯一短链全部解析成功。
  只在没有代理、解析失败时才退回 `urls[]` 的 1:1 匹配（数量相等才换）；不匹配就保留短链——「短链没展开」是可接受的降级，「短链指向错的站」才是事故。
- **自指短链要删，不是替换**：推文末尾的 t.co 多半指向它自己的视频/图片，替换后就是「这条推文链接到它自己」。媒体块、引用块已经在展示，删掉这一行。
- **x.com 内部链接要删**：解析结果可能是 `x.com/i/onboarding/...`、登录墙等导航页，那不是内容。判断标准只看得到域名和路径：`x.com/i/`、`/login`、`/settings`、`/home` 一律删。
- **作者链接不能碰**：历史同步的 memo 以 `[@作者](https://x.com/handle/status/<id>)` 开头，它就是这条 memo 的 tweet id 来源。清短链时只换 `t.co`，不要对历史 memo 做「删自指链接」。
- 推文自带 markdown 标题（`#`、`##`）要**降 2 级**（→ `###`、`####`），否则原文标题会盖过卡片标题。
- 折叠连续空行：memos 忠实渲染每个换行，3 个以上空行会撑出大洞。

### 4. 引用块：转推的实体

- 用 `> ` 前缀整段包裹（含空行用单独的 `>`），memos 渲染成引用块。
- 引用里保留作者、链接、原文全部，**引用里的图片也保留**（转推的图常常是主体）。
- 引用段落内同样降标题级别，避免层级倒挂。

### 5. 媒体

- 照片：`![](https://pbs.twimg.com/media/xxx.jpg?name=large)` —— 裸 URL 拿到的是缩略图，`name=large` 是 1200px 版本。memos 允许 https 外链图片（`referrerPolicy=no-referrer`）。
- 视频：`🎬 [视频 · 1920×1080](https://video.twimg.com/…)` —— memos 不内嵌推特视频，链接即最优解，带上尺寸让读者判断是否值得点。
- 多图不用表格/拼图：memos 会把每张图按原比例竖排，这比缩略图网格更好看。
- 本机无法访问 pbs/video 域名，**不要下载后上传附件**（会失败，也浪费流量）；热链由读者的浏览器拉取。

### 6. 链接区：让 memos 自己生成预览卡

裸 URL 独占一个段落时，memos 会渲染成 LinkMetadataCard（标题+描述+缩略图），比 `[文字](url)` 好看得多，信息量也更大。所以：

- 只放「额外资源」链接（`urls` 里非媒体、非本推的），一行一个 URL，前面加 `**🔗 链接**` 小标题。
- 已经内联进正文的 URL 不重复列——短链换成真实地址后，正文里有了，链接区自然就不列了。
- 同一推文自身的链接不列（那是来源，不是资源）。

### 7. 长文：`<details>` 折叠

memos 支持 `<details>/<summary>`（白名单 HTML）。文章全文折进去，列表里只占一行，点开是完整存档。summary 写 `📄 全文 · N 字`，字数本身就是「值不值得点」的信号。

### 8. 尾部：来源 + 标签

- `[原推](url) · 存档 YYYY-MM-DD`：可回溯，且能被后续去重扫描（正则 `/status/(\d+)`）。
- 标签行放最后：`#Twitter #Bookmark` 是既有归档的一致性锚点（771 条历史都带），后面跟 0–3 个主题标签。
- 主题标签只从历史词表里选（`#github #Codex #AI #skill #ClaudeCode #Agent …`），新造标签会让归档碎片化。最多 3 个，宁缺勿滥。

## 不要做的事

| 反模式 | 原因 |
| --- | --- |
| `## 标题` 或 `# 标题` 当卡片标题 | 压过相邻卡片；列表预览里层级错乱 |
| 用表格做元信息 | 瀑布流里表格列宽不可控，窄屏横向滚动 |
| 用 `<mark>` 高亮 | memos HTML 白名单会丢弃 |
| 把 `> [!NOTE]` 用在普通引用上 | 那是「提示框」，语义被稀释；普通引用用 `> ` 就够 |
| 一条 memo 放多条书签 | 破坏「一个 id 一条 memo」的去重契约，也不可单独链接 |
| 输出 `[链接](url)` 包裸 URL | 丢掉预览卡的标题/描述/缩略图 |
| 下载媒体再上传 | 本机出网受限；附件会撑爆 instance 存储 |
| 每条都堆 5 个标签 | 标签失去区分度，检索反而更差 |

## 可选的强化（按需，不默认）

- **多个高价值书签做成周报**：`<details>` 折叠每条一句话摘要 + 原推链接，标签 `#Twitter #Bookmark #周报`。日报/周报是「编排」层的产物，不做成单条 memo 的替代。
- **代码片段**：推文含代码时用围栏代码块并标注语言（memos 有 highlight）。
- **`> [!TIP]`**：只在整条 memo 是方法论/清单时用一次，位置在正文之前。

## 验收清单

发布前逐条自查（`scripts/render.py` 已自动满足 1–8）：

1. 首行是 `### ` 标题，且正文里没有重复这一句。
2. byline 一行，无空段、无尾随 `·`。
3. 正文无 3 个以上连续空行，无残留 `# ` / `## ` 顶级标题。
4. 引用块每行都以 `>` 开头（含空行）。
5. 照片带 `?name=large`；视频有 `🎬` 和尺寸。
6. 链接区每个 URL 独占一行且不带 markdown 链接语法。
7. `<details>` 有 `<summary>`，前后有空行（否则不渲染）。
8. 最后两行：`[原推](…) · 存档 …` 和标签行。
